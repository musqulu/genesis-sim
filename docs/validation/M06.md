# M06 validation — recorded cognition and deterministic scheduling

Date: 2026-11-08. Status: **implemented; automated tests passed; roadmap manual test passed in Chromium (Playwright) on an isolated stack; live backend upgraded and verified — a human visual pass is still recommended**.

## Delivered scope

- **Provider contract** (`providers/base.py`). It covers:
  - `ProviderIdentity` (a revision of `None` means unknown, never "pinned");
  - `Capabilities` (structured output declared, not assumed);
  - `Usage` (unknown values stay `None`, never zero);
  - `ProviderResponse` (raw text plus the request id and input hash it answers);
  - a typed `ProviderError`, retryable only for timeout, unavailable, transport and rate-limited errors.

  The same contract is meant for M07A (MLX-LM) and M07B (HTTP).
- **Providers.**
  - `RecordedProvider` answers strictly by **input hash**. A mismatch is a non-retryable technical error; responses are never matched by call order.
  - `ScriptedProvider` serves the M04/M05 fixture scripts as raw JSON through the same path.
  - Recordings are generated from the real engine, context builder and parser (`uv run python -m genesis.providers.record`, with `--check` to verify) and stored in `providers/recordings/`.
- **Context** (`cognition/context.py`). A request is plain JSON data only: the observation, the previous decision result, an action JSON schema whose limits come from the run's rules, and the response format.
  - The previous decision result is derived from recorded events, so a rejection has no state effect.
  - The input hash binds the actor, target tick, schema version and context, and excludes the run id so recordings match fresh runs of a fixture.
  - No world, database or engine object crosses the boundary.
- **Strict parsing** (`cognition/policy.py`, Pydantic strict mode). Checks run in this order:
  1. empty output;
  2. size limit of 4096 characters;
  3. JSON syntax, with duplicate keys treated as malformed;
  4. the value must be an object;
  5. exact types with no unknown fields;
  6. this run's per-action limits.

  A failure becomes an `Unparsed` outcome that is recorded and consumes the opportunity. There is no fallback action and no retry.
- **Cadence rules** (`engine/cadence.py`, state schema 6, rules `m06-rules-1`):
  - A decision is due on the first tick, every 4 ticks, or early when the organism's own local view total (energy plus loose material) has changed by at least 10. At most one decision per tick.
  - A 1-energy cognition fee is charged per opportunity. If that kills the organism it is recorded as starvation and no request is made.
  - All observations come from the same post-fee state before any action. Resolution follows stable id order rotated by tick, never response arrival.
  - Scheduler state (`last_decision_tick`, `view_total_at_decision`) is hashed.
- **Tick barrier** (`engine/world.py` `prepare_tick`/`finish_tick`, `runtime/scheduler.py`, `runtime/runner.py`):
  - Requests are persisted to `request_records` before dispatch.
  - A bounded single-worker queue handles inference (`queue_capacity` 4), and responses are stored durably as they arrive.
  - The tick commits only when every response is present and the run is running or one Step was authorized. It commits atomically with the `decision_attempts` rows; the unique `(run_id, request_id)` pair is the consumption key.
  - Pause keeps pending responses and commits nothing.
  - One transport retry, then a technical pause with no ecological time passing. Resume or Step retries the same request.
  - Stale responses (from an earlier generation) and duplicate responses are refused and noted in `technical_log`.
  - On recovery, an identical recomputed request reuses its stored response, so the provider is not called again and costs are not charged twice.
- **Inspection.**
  - A *Decision inspector* lists each attempt and shows the request id, input hash, provider, the previous result and observation given, the **verbatim raw output as text**, the parse status and error, the parsed proposal, the engine outcome with an event link, and usage (with "unknown" where unavailable).
  - The run controls show pending work separately from the committed tick, and the world header labels the provider "not a live model".
- **Fixtures** (dev only): `recorded_valid`, `recorded_invalid`, `recorded_delayed` (3 s per response) and `recorded_mismatch`. The M04/M05 fixtures keep every-tick, fee-free decisions through labeled fixture parameters, so their outcomes are unchanged.
- **API.**
  - New: `GET /api/decisions`, `GET /api/decisions/{request_id}`, `GET /api/requests`.
  - The frame contract is v6, adding `pending` and `provider`.
  - Database layout 5 is reached by an additive 4→5 migration.
- **Compatibility.** Schema 2–5 runs keep their rules and hashes. Schema ≤5 organisms still use the legacy every-tick engine path.

Not added: real inference (M07), autonomous plans, embeddings, tools for models, or retry loops to force valid output. No model was installed or downloaded. `AGENTS.md` is unchanged.

## Behaviour changes and fixes

1. **Layering change (intended, per architecture).** The action schema now enforces per-action amount limits at the parse boundary. Over-limit requests from the M05 workshop script (extract 11, pack 3) are therefore recorded as `Unparsed: schema_invalid` instead of the engine's `over_action_limit`. The state effect is identical (none). The engine check remains as a second line of defence and is still unit-tested. The M05 browser expectations and README steps were updated.
2. **Context normalization.** The request context contained Python tuples. It is now normalized to exact wire JSON. Hashes were unchanged, because canonical JSON is identical.
3. **Stale pending progress.** The frame-equality shortcut ignored `pending`, so arriving responses were not shown while paused. Fixed, with a test.
4. **Reducer schema default.** Organism serialization defaulted to schema 5, dropping scheduler fields during reduction. Fixed by defaulting to the latest schema.
5. **Test races** in my own tests (resume without a stop tick; selector ambiguity) were fixed in the tests.

## Known limits / unverified

- **Human visual check** of the inspector and pending note is still pending.
- **One provider at a time:** inference is sequential with concurrency 1. The queue bound is tested with six organisms, but population-scale scheduling is M09.
- **Coarse local-change trigger:** it fires on inflow ticks when ≥ 10 energy appears in view. That is a proposed default whose behavioural effect is an open question.
- **Wall-clock timeout:** Step waits at most 5 s and then returns with the tick still pending. The pending tick commits later, once responses arrive.
- **Recorded and scripted responses only.** They are diagnostics of the contract, not evidence of autonomous behaviour. Live MLX-LM and API adapters are M07A/M07B, which need approval and a model or endpoint choice.

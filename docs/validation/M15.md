# M15 validation — technical health and safe recovery

Date: 2026-11-12. Status: **implemented; automated tests passed (including real `kill -9` process crashes); health and backup check passed in Chromium (Playwright).** No state-schema, DB-layout or frame change.

## What was already in place (M03–M14) and is now proven under failure

- **Atomic ticks:** events, deltas, ledger, projections, decision attempts and snapshots are written in one transaction.
- **Recovery on startup:** the run is rebuilt from the latest valid snapshot plus recorded events and verified against the recorded hashes.
- **Persisted requests:** model requests are saved, so a stored response is reused after a restart rather than asked twice.
- **Provider failures:** these cause technical pauses, never fallbacks.

## Added

| | |
|---|---|
| **Health** (`ops/health.py`, `GET /api/health` → `report`) | • last durable tick against the live tick;<br>• decision barrier and queue (capacity, deepest seen);<br>• the provider worker's own health;<br>• the ledger check;<br>• disk (free, minimum, database size);<br>• inference metrics (decisions, unparsed, median latency, provider failures);<br>• the last 20 technical notes.<br>The status is `ok`, or `attention` with problems such as `low_disk`, `ledger_imbalance`, `durable_tick_mismatch` or `technical_pause`. |
| **Recovery notes** | The technical log now records:<br>• every **load** (restored from snapshot/initial + replayed ticks, verified);<br>• every **reused stored response** after a restart;<br>• every **tick failure** or **invariant failure** that paused the run.<br>Notes are technical only. |
| **Disk guard** | Before each tick attempt (checked at most every 5 s): if free space is below `GENESIS_MIN_FREE_MB` (default 512), the run takes a technical pause *before* the tick. No ecological time passes, and a `low_disk` note is recorded. |
| **Safe mode for failed verification** | If recorded history fails verification at startup (corrupt data, missing active reference), the server **still starts**, in safe mode:<br>• `/api/health` reports `storage_error` with the reason;<br>• every run endpoint answers 503 with that reason;<br>• nothing is changed, repaired or replaced.<br>Before M15 the server refused to start. The page shows a *Recorded history needs attention* alert instead of "disconnected". |
| **Verified backups** (`ops/recovery.py`) | `POST /api/backups` writes a consistent copy to `data/backups/` (the SQLite online backup) and verifies it: `PRAGMA integrity_check`, then **every run's latest tick is replayed from the copy** and compared with its recorded hash. The result is stored beside it. `GET /api/backups` lists them.<br>`python -m genesis.ops.recovery verify <file>` and `… restore <backup> <new path>` give a restore check: copy to a **separate** path and open it as the observer would. Restoring over the live database or an existing file is refused. |
| **Dashboard → Technical health** | Status, durable/live tick, barrier, worker, inference, ledger, disk, **Back up & verify**, the backup list and technical notes. *"Technical recovery pauses logical time; it never changes the world, rescues organisms or reseeds an extinct run."* |

Not added: self-repair, automatic restore, retention or deletion policies, or infrastructure monitoring.
